Architecture de la fenêtre d'analyse

Une console Python Tkinter, intégrable dans une autre application et capable d'appeler ses fonctions. Les scripts peuvent aussi être exécutés sans fenêtre, puis vérifiés dans l'historique. Cette page montre comment le code est découpé et ce qui se passe lors d'une exécution.

Modules et dépendances

Le projet est séparé en deux couches. Les widgets affichent et transmettent les actions de l'utilisateur. La logique n'importe pas Tkinter et peut donc être utilisée seule. AnalysisSession est le point d'entrée de la logique : elle possède le CodeExecutor et l'historique. AnalysisPanel est le seul module qui relie les deux couches.

───▶ crée ou utilise widget logique

Les modules échangent aussi des objets de données immuables : ExecutionResult (sorties et erreur), HistoryEntry (code, résultat, fichier d'origine), SessionEvent (modification de la session) et VariableInfo (variable à afficher). main.py place le panneau directement dans une fenêtre tk.Tk. Une application hôte passe plutôt par AnalysisWindow, et peut lui fournir sa propre session.

Disposition de la fenêtre

AnalysisPanel._build_layout imbrique deux ttk.PanedWindow : un séparateur horizontal coupe la fenêtre en deux colonnes, et un séparateur vertical coupe la colonne de gauche en deux. Tous les séparateurs se déplacent à la souris. Chaque zone possède une barre de défilement verticale et une horizontale, placées par attach_scrollbars.

▶ Exécuter

Les widgets ne connaissent pas la session. Chacun reçoit à sa création la fonction à appeler lors d'un clic (on_execute, on_clear, on_reset). Le panneau fournit ces fonctions. Pour Effacer et Réinitialiser, il demande d'abord une confirmation avec messagebox.askyesno.

Session et événements

AnalysisSession regroupe tout ce qui doit survivre à la fenêtre : l'exécuteur, donc les variables, et l'historique des exécutions. Elle ne dépend pas de Tkinter. Une application peut donc exécuter des scripts sans rien afficher, puis ouvrir la fenêtre plus tard sur la même session. 

session = AnalysisSession(context={"app": self})
session.run("x = 1")                      # aucune fenêtre
session.run_file("scripts/analyse.py")    # idem, depuis un fichier
AnalysisWindow(self, session=session)     # affiche les deux exécutions et x

Méthodes

Abonnement du panneau

  1. Rattrapage. À sa création, le panneau affiche chaque entrée de session.history puis les variables actuelles.
    AnalysisPanel.__init__
  2. Abonnement. Il appelle session.subscribe(self._on_session_event). La session appellera cette fonction avec un SessionEvent à chaque modification, quelle qu'en soit l'origine : bouton du panneau, application hôte ou autre panneau partageant la session.
  3. Réaction. ENTRY_ADDED ajoute l'entrée à l'historique et rafraîchit les variables. HISTORY_CLEARED vide l'historique. NAMESPACE_RESET rafraîchit les variables.
    AnalysisPanel._on_session_event
  4. Désabonnement. À la destruction du panneau (fermeture de la fenêtre), l'événement Tk <Destroy> déclenche session.unsubscribe. La session continue d'exister et garde tout.
    AnalysisPanel._on_destroy

Le bouton Exécuter suit le même chemin : le panneau appelle session.run et ne met pas l'affichage à jour lui-même. C'est l'événement ENTRY_ADDED qui s'en charge, ce qui garantit un seul chemin de mise à jour.

Déroulement d'une exécution

Voici ce qui se passe entre le clic sur ▶ Exécuter et la mise à jour de l'affichage.

  1. Le bouton appelle le panneau. EditorFrame appelle la fonction on_execute reçue à sa création.
    editor_frame.py → AnalysisPanel._execute_code
  2. Le panneau transmet le code à la session. get_code() retourne le texte saisi. S'il n'est pas vide, le panneau appelle session.run(code).
    analysis_panel.py
  3. Les sorties sont redirigées. CodeExecutor.execute remplace temporairement sys.stdout et sys.stderr par un même io.StringIO, avec contextlib.redirect_stdout et redirect_stderr. Tout print exécuté pendant le script est écrit dans ce tampon et non dans la console. Cela vaut aussi pour les fonctions de l'application hôte appelées par le script.
    code_executor.py · execute
  4. Le script est analysé puis exécuté. _run transforme le code en arbre syntaxique avec ast.parse. Si la dernière instruction est une expression, elle est mise de côté. Le reste est exécuté avec exec dans l'espace de noms persistant, puis l'expression est évaluée avec eval. Sa valeur est affichée avec repr si elle n'est pas None, comme dans une console Python.
    code_executor.py · _run
  5. Les erreurs sont capturées. Exception et SystemExit sont interceptées pour que l'application reste ouverte. _user_traceback retire les frames internes, jusqu'à la première frame dont le fichier est <script> : le traceback commence donc au code de l'utilisateur.
    code_executor.py · _format_exception, _user_traceback
  6. Le résultat est enregistré. L'exécuteur retourne un ExecutionResult(output, error). La session l'enveloppe dans une HistoryEntry, l'ajoute à l'historique, puis prévient ses abonnés avec SessionEvent(ENTRY_ADDED, entry).
    analysis_session.py · run, _record, _notify
  7. L'historique est complété. HistoryFrame.add_entry ajoute l'éventuel # Fichier : …, puis le code précédé de >>> et ..., la sortie et l'erreur, chacun avec son style. Le widget repasse ensuite en lecture seule et défile jusqu'en bas.
    history_frame.py
  8. Les variables sont extraites et classées. inspect_variables parcourt l'espace de noms, ignore les noms commençant par _ et les modules, et produit un VariableInfo par variable, avec sa catégorie.
    variable_inspector.py
  9. Le tableau est reconstruit. VariablesFrame.refresh note les groupes repliés, vide le Treeview, insère un groupe par catégorie non vide, puis élargit si besoin la colonne Valeur.
    variables_frame.py

Tout cela se déroule dans le fil de l'interface Tkinter. C'est ce qui permet au script de manipuler les widgets de l'application hôte sans risque, mais c'est aussi pourquoi un calcul long fige la fenêtre. Pour la même raison, les méthodes de la session doivent être appelées depuis ce fil lorsqu'un panneau y est abonné.

Tableau des variables

Le classement est fait par classify, dans la couche logique. Les tests sont appliqués dans cet ordre, et le premier qui réussit détermine la catégorie :

OrdreTestCatégorieValeur affichée
1isinstance(value, type)Classesrepr
2callable(value)Fonctionsnom et signature (inspect.signature)
3int, float, complex (donc bool)Nombresrepr
4str, bytes, bytearrayTextesrepr
5collections.abc.CollectionCollectionsrepr
6tout le resteObjetsrepr
  • Les classes sont testées avant les fonctions, car une classe est elle aussi appelable.
  • Les valeurs sont ramenées sur une ligne et coupées à 100 caractères. Si repr échoue, la valeur affichée est <valeur indisponible>.
  • Les couleurs sont un détail d'affichage : elles sont définies dans CATEGORY_COLORS (variables_frame.py), et appliquées par des tags du Treeview. L'en-tête de chaque groupe est en gras et indique le nombre de variables.
  • Les colonnes Nom et Type ont une largeur fixe. La colonne Valeur s'élargit avec le panneau, mais sa largeur minimale est celle de la valeur la plus longue : la barre horizontale permet alors de tout lire.

Accès à l'application hôte

Le dictionnaire context passé à la session (ou à AnalysisWindow et AnalysisPanel, qui créent alors leur propre session) devient le point de départ de l'espace de noms du CodeExecutor. Cet espace de noms sert ensuite de variables globales à tous les scripts. 

# code_executor.py
def reset(self) -> None:
    self._namespace.clear()
    self._namespace.update(self._context)
    self._namespace["__name__"] = "__main__"
  • Les objets du contexte sont les mêmes objets que ceux de l'application, et non des copies : measures.append(1) modifie bien la liste de l'hôte.
  • Réaffecter un nom (measures = []) ne change que l'espace de noms de la session. L'application conserve ses données.
  • reset est appelé à la création de l'exécuteur et par reset_namespace. Il vide le dictionnaire sur place, ce qui garde valides les références à namespace, puis remet le contexte initial. Les modifications internes aux objets du contexte ne sont pas annulées.
  • __name__ est placé en dernier : le contexte ne peut donc pas le remplacer. Les classes définies dans un script sont ainsi rattachées à __main__.
  • L'espace de noms est conservé d'une exécution à l'autre, tant que la session existe.

Le paquet analyse_app expose AnalysisPanel, AnalysisWindow, AnalysisSession, ExecutionResult, HistoryEntry, SessionEvent et EventKind (voir __init__.py). Les autres modules sont des détails internes.

Faire évoluer le projet

  • Ajouter une zone (par exemple un graphique) : créer un nouveau ttk.LabelFrame dans son propre fichier, l'ajouter dans AnalysisPanel._build_layout, puis le mettre à jour dans AnalysisPanel._on_session_event.
  • Ajouter une action sur la session (par exemple enregistrer l'historique dans un fichier) : ajouter la méthode à AnalysisSession, un membre à EventKind si l'affichage doit réagir, puis traiter cet événement dans le panneau.
  • Changer la façon d'exécuter le code (fil séparé, délai maximal…) : CodeExecutor et AnalysisSession.run sont concernés. Les widgets ne dépendent que d'ExecutionResult et des événements.
  • Changer les catégories de variables : modifier Category et classify dans variable_inspector.py, puis la couleur correspondante dans CATEGORY_COLORS.
  • Tester sans interface : AnalysisSession, CodeExecutor et inspect_variables s'utilisent directement, sans créer de fenêtre (voir exemples/04_sans_interface.py).
