Architecture de la fenêtre d'analyse

Une console Python Tkinter, intégrable dans une autre application et capable d'appeler ses fonctions. Cette page montre comment le code est découpé et ce qui se passe quand on clique sur ▶ Exécuter.

Modules et dépendances

Le projet est séparé en deux couches. Les widgets affichent et transmettent les actions de l'utilisateur. La logique n'importe pas Tkinter et peut donc être testée ou réutilisée seule. AnalysisPanel est le seul module qui relie les deux.

───▶ crée ou utilise - - -▶ importe seulement un type de données widget logique

main.py place le panneau directement dans une fenêtre tk.Tk. Une application hôte, comme exemple_application.py, passe plutôt par AnalysisWindow, qui l'ouvre dans une fenêtre secondaire.

Disposition de la fenêtre

AnalysisPanel._build_layout imbrique deux ttk.PanedWindow : un séparateur horizontal coupe la fenêtre en deux colonnes, et un séparateur vertical coupe la colonne de gauche en deux. Tous les séparateurs se déplacent à la souris.

Déroulement d'une exécution

Voici ce qui se passe entre le clic sur le bouton et la mise à jour de l'affichage.

  1. Le bouton appelle le panneau. EditorFrame ne connaît pas le moteur d'exécution : il reçoit à sa création une fonction on_execute et l'appelle au clic.
    editor_frame.py → AnalysisPanel._execute_code
  2. Le panneau lit le code. get_code() retourne le texte saisi. Si le texte est vide ou ne contient que des espaces, rien ne se passe.
    analysis_panel.py
  3. Les sorties sont redirigées. CodeExecutor.execute remplace temporairement sys.stdout et sys.stderr par un même io.StringIO, avec contextlib.redirect_stdout et redirect_stderr. Tout print exécuté pendant le script est écrit dans ce tampon et non dans la console. Cela vaut aussi pour les fonctions de l'application hôte appelées par le script.
    code_executor.py · execute
  4. Le script est analysé puis exécuté. _run transforme le code en arbre syntaxique avec ast.parse. Si la dernière instruction est une expression, elle est mise de côté. Le reste est exécuté avec exec dans l'espace de noms persistant, puis l'expression est évaluée avec eval. Sa valeur est affichée avec repr si elle n'est pas None, comme dans une console Python.
    code_executor.py · _run
  5. Les erreurs sont capturées. Exception et SystemExit sont interceptées pour que l'application reste ouverte. _user_traceback retire les frames internes, jusqu'à la première frame dont le fichier est <script> : le traceback commence donc au code de l'utilisateur.
    code_executor.py · _format_exception, _user_traceback
  6. Le résultat est retourné. Un objet immuable ExecutionResult(output, error) regroupe le texte capturé et le traceback éventuel.
  7. L'historique est complété. HistoryFrame.add_entry ajoute le code précédé de >>> puis ..., la sortie, puis l'erreur, chacun avec son style. Le widget repasse ensuite en lecture seule et défile jusqu'en bas.
    history_frame.py
  8. Les variables sont extraites. inspect_variables parcourt l'espace de noms et ignore les noms commençant par _ ainsi que les modules. Pour chaque variable, il produit un VariableInfo dont la valeur est ramenée sur une seule ligne et coupée à 100 caractères. Si repr échoue, la valeur affichée est <valeur indisponible>.
    variable_inspector.py
  9. Le tableau est remplacé. VariablesFrame.refresh vide le Treeview puis y insère une ligne par variable.
    variables_frame.py

Tout cela se déroule dans le fil de l'interface Tkinter. C'est ce qui permet au script de manipuler les widgets de l'application hôte sans risque, mais c'est aussi pourquoi un calcul long fige la fenêtre.

Accès à l'application hôte

Le dictionnaire context passé à AnalysisWindow ou à AnalysisPanel devient le point de départ de l'espace de noms du CodeExecutor. Cet espace de noms sert ensuite de variables globales à tous les scripts. 

# code_executor.py
self._namespace = {**(context or {}), "__name__": "__main__"}
  • Les objets du contexte sont les mêmes objets que ceux de l'application, et non des copies : measures.append(1) modifie bien la liste de l'hôte.
  • Réaffecter un nom (measures = []) ne change que l'espace de noms de la fenêtre d'analyse. L'application conserve ses données.
  • __name__ est placé en dernier : le contexte ne peut donc pas le remplacer. Les classes définies dans un script sont ainsi rattachées à __main__.
  • L'espace de noms est conservé d'une exécution à l'autre, tant que le panneau existe.

Le paquet analyse_app n'expose que AnalysisPanel et AnalysisWindow (voir __init__.py). Les autres modules sont des détails internes.

Faire évoluer le projet

  • Ajouter une zone (par exemple un graphique) : créer un nouveau ttk.LabelFrame dans son propre fichier, puis l'ajouter dans AnalysisPanel._build_layout et le mettre à jour dans _execute_code.
  • Changer la façon d'exécuter le code (fil séparé, délai maximal…) : seuls CodeExecutor et AnalysisPanel._execute_code sont concernés. Les widgets ne dépendent que d'ExecutionResult.
  • Changer les variables affichées (montrer les modules, détailler les dictionnaires…) : tout se trouve dans variable_inspector.py.
  • Tester sans interface : CodeExecutor et inspect_variables s'utilisent directement, sans créer de fenêtre.
